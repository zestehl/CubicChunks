# Preliminary correctness and JVM optimization audit

Reviewed October 13, 2026 against fork commit `6c935218a21bc04c66c77d4db8a6ba4d036516cd`. Scope: the current CubicChunks core/API, storage, asynchronous task lifecycle, lighting/heightmaps, packet encoding, watcher collections and client render cache, with Riven integration considered through the retained native profile. Production algorithms and loader pins are unchanged in this pass.

Follow-up: the [first lighting/configuration batch](LIGHTING-FIRST-PASS.md) fixes the live lighting-height snapshot and deduplicates surface-height notifications. Both loader artifacts passed local checks. The matched current-runtime `lighting-pass-02` passed eleven native scenarios and independent marker inspection; the earlier mixed-runtime run remains separately labeled. Findings below describe the original audit state; the other candidates remain open. The repaired vertical-render-distance option supports an explicit renderer diagnostic, not full-height Celeritas qualification.

The [scheduled-tick batch](SCHEDULED-TICK-PASS.md) subsequently repairs finding 2 and related set/list index contracts. Both loaders passed local checks; the native baseline completed torch/water callbacks at all 32 allocated cube levels and preserved the stored marker fixture. Other findings remain open. Renderer/shader investigation is now deferred at the user's request.

**The first useful changes are ownership/collection fixes and reductions in repeated work.** Java 25 supplies useful experiments, but the existing native runtime already receives its compiler and runtime improvements. New syntax or a newer executor alone does not remove the work identified here.

The [retained native suite](measurements/cubic-lab-v1/README.md) observes a **314.42 ms maximum tick** during a resident-lookup scenario overlapping **6,140 cube-data save events**, with **zero reported GC collections in that scenario**. Synchronous cube-to-NBT serialization remains on the world thread. Streaming also contains substantial Riven generation: horizontal attribution is 124 Riven / 57 CubicChunks samples out of 216; vertical is 63 / 17 out of 108. Those are stack-path samples, not CPU percentages. The renderer's horizontal window has 22 `RenderChunk` rebuild samples out of 105; this is a reason to inspect rebuild/cache behavior, not evidence of exclusive CubicChunks renderer cost.

## Correctness candidates

“Reproduced” below means ordinary isolated JVMs using the actual existing named build classes and Minecraft dependencies. No game, coremod, world or graphical client was booted. Java 8 and Java 25 observations agree. “Source” means a reachable code/ownership concern that still needs its specific failure or native fixture.

| Order | Finding | Evidence and affected behavior | First verification/fix direction |
| --- | --- | --- | --- |
| 1 | Lighting save metadata borrows a live height array | **Source + NBT alias reproduced.** [LightingManager:122](../src/main/java/io/github/opencubicchunks/cubicchunks/core/lighting/LightingManager.java#L122) passes the column's live `int[]` directly to `setIntArray`. `IHeightMap.HeightMap` shares that same vanilla column array, and queued saves retain the NBT object. Actual `NBTTagIntArray` retains its input in both named Minecraft builds. Later height changes can alter a queued lighting snapshot while compression reads it. | Clone the lighting height snapshot before publishing it. Verify queued-save bytes/metadata remain unchanged after subsequent height mutations, including a delayed writer. Preserve the earlier block-light, sky-light and biome snapshot fixes. |
| 2 | Scheduled-tick collection operations fail their contracts | **Reproduced.** [CubeSplitTickSet:209](../src/main/java/io/github/opencubicchunks/cubicchunks/core/util/world/CubeSplitTickSet.java#L209) wraps an iterator without implementing `remove`. The outer iterator calls it; inherited `AbstractSet.clear` also depends on it. Nonempty `clear` and iterator removal throw `UnsupportedOperationException`. [CubeSplitTickList:133](../src/main/java/io/github/opencubicchunks/cubicchunks/core/util/world/CubeSplitTickList.java#L133) updates the list but returns `null` instead of the prior entry. `MixinWorldServer` installs these collections in real worlds. | Restore supported removal/clear and the list return value. Check the global collection and `byCube` index after iterator removal, retain/remove/clear and replacement. Keep the existing equals/ordering collision workaround intact. Native scheduled blocks/liquids need coverage beyond the lab's gold markers. |
| 3 | Default storage batch reads reject missing entries | **Reproduced.** [ICubicStorage:126](../CubicChunksAPI/src/main/java/io/github/opencubicchunks/cubicchunks/api/world/storage/ICubicStorage.java#L126) collects nullable `readColumn`/`readCube` results using `toConcurrentMap`; both missing-column and missing-cube cases throw `NullPointerException`. The interface documents missing data as `null`. | Define and preserve the batch's missing-entry representation, then use a collector/map strategy that supports it. Verify missing, present, mixed and I/O-error batches. Current native single-cube reads do not exercise this default API. |
| 4 | Heightmap deserialization is unsafe for instance reuse | **Reproduced.** [ServerHeightMap:747](../src/main/java/io/github/opencubicchunks/cubicchunks/core/world/ServerHeightMap.java#L747) leaves an old segment array when an incoming count is zero and does not invalidate `heightMapLowest`. Reloading an empty 2,560-byte payload into a populated instance reserializes 2,572 bytes; a previously cached minimum of 32 remains 32 after reading empty data. | Clear absent segments and invalidate derived caches; verify repeated populated/empty reloads and exact bytes. The usual column load constructs a fresh map, so this is especially a prerequisite for future pooling/reuse, not a reproduced native-world failure. |
| 5 | Compression failure loses explicit buffer cleanup | **Source.** [RegionCubeStorage:207](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/chunkio/RegionCubeStorage.java#L207) retains successful `ByteBuf`s inside a parallel collector. If another entry fails, its partial result is not returned to `writeBatch`, whose `finally` cannot release those retained results. | Inject failure after successful entries; retain ownership of every buffer until the operation completes/fails and release all completed results. Distinguish missing `release` from permanent memory retention: eventual cleaner behavior depends on the allocator. Fix ownership before increasing concurrency. |
| 6 | Save failures and interruption lack a reliable completion outcome | **Source.** [AsyncBatchingCubeIO:284](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/chunkio/AsyncBatchingCubeIO.java#L284) logs an `IOException` and keeps failed entries pending; blocking drain can continue indefinitely under persistent failure. `flush`/`close` catch interruption, log it and return without a completed drain. | Use fault-injected storage for persistent/transient failure and interruption. Keep failed snapshots, propagate a meaningful flush/close failure, and define retry/backpressure policy. Never report durability merely because a dirty flag was cleared at enqueue time. |
| 7 | Closing one cubic world stops global loading executors | **Source.** [AsyncBatchingCubeIO:242](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/chunkio/AsyncBatchingCubeIO.java#L242) calls global [shutdownNowBlocking:326](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/chunkio/async/forge/AsyncWorldIOExecutor.java#L326), which clears task maps across worlds. The source already identifies this remaining lifecycle limitation. | Add two cubic worlds with loads in flight, unload one, and verify other-world completion, cancellation identity and column pins. The existing lab uses one cubic overworld and cannot qualify this path. Consider world-owned services/lifecycle before replacing the executors. |
| 8 | A newly constructed lighting queue reports nonempty | **Reproduced.** [PooledLightUpdateQueue:46](../src/main/java/io/github/opencubicchunks/cubicchunks/core/lighting/phosphor/PooledLightUpdateQueue.java#L46) leaves `empty` at the default `false` while size is zero. The engine consults it for pending-work and early-return checks. | Initialize the flag consistently and verify construction/add/drain/reuse. This is a small startup-state defect, not evidence of a sustained lighting slowdown. |

Additional source paths worth targeted checks are the watcher iterator's lookahead/removal behavior, null-column packet decoding, reservation-failure lock cleanup, and exposed mutable per-column collections. They are not promoted to confirmed in-game bugs by this audit.

## Performance work with a concrete target

These changes can largely remain Java 8-compatible. Their operation counts are derived from the code, not measured speedups.

| Candidate | Current work | Proposed experiment and evidence |
| --- | --- | --- |
| Deduplicate surface-height notifications | [LightingManager:169](../src/main/java/io/github/opencubicchunks/cubicchunks/core/lighting/LightingManager.java#L169) iterates a **17 × 17 × 17** inclusive box and calls `heightUpdated(x,z)` for each position. Only **17 × 17** X/Z pairs matter; [ColumnWatcher:233](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/ColumnWatcher.java#L233) sets a dirty bit. That is **4,913 → 289 calls per tracked cube** with the same current X/Z footprint. | Use a two-dimensional traversal and retain the existing extra edge coverage. Compare dirty-coordinate sets, boundary skylight, column update packets and horizontal/vertical tick tails. This method appears in the retained streaming profile. |
| Remove empty-cube packet padding | [WorldEncoder:232](../src/main/java/io/github/opencubicchunks/cubicchunks/core/network/WorldEncoder.java#L232) reserves 1,024 heightmap bytes for **every** cube, while encoding writes heights only for nonempty cubes. [PacketCubes:72](../src/main/java/io/github/opencubicchunks/cubicchunks/core/network/PacketCubes.java#L72) sends the whole allocated array. Each empty cube therefore adds **1,024 trailing zero bytes** to the uncompressed body. | Compute the exact encoded size or use the actual writer index. Test empty/mixed/biome-bearing/skylit packets with unchanged decoding and tile entities. Measure allocation and serialized bytes; network compression may make the wire savings much smaller. |
| Bound and isolate save work | [CubeProviderServer:212](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/CubeProviderServer.java#L212) scans and submits all dirty cubes; [IONbtWriter:158](../src/main/java/io/github/opencubicchunks/cubicchunks/core/server/chunkio/IONbtWriter.java#L158) resolves **4,096 block states per storage-bearing cube**. Compression uses the shared common pool, and queue snapshots cover the full pending maps. | First reduce state-ID lookup/packing overhead while preserving `Blocks`, `Data`, `Add`, `Add2`, events, capabilities and entity/tick data. Then evaluate bounded autosave submission and a dedicated bounded compression executor with a small-batch serial path. Keep explicit flush/save-all completion and immutable owner-thread snapshots. Track tick max, pending bytes, compression jobs, flush latency and reload correctness. |
| Improve staging height queries | [StagingHeightMap:50](../src/main/java/io/github/opencubicchunks/cubicchunks/core/world/StagingHeightMap.java#L50) sorts on every insertion and dirties all 256 block columns for a nonempty cube. A dirty query scans staged cubes and up to 16 block states per cube. | Compare sorted insertion and per-cube opacity/top summaries with precise invalidation. Exercise negative Y, gaps, caves, translucent/custom blocks and staged-to-tracked transitions. Avoid introducing a stale cache to remove a scan. |
| Reduce watcher maintenance allocation/scanning | `PlayerCubeMap` supplies fresh player lists to several sorting lists each tick. [WatchersSortingList3D:131](../src/main/java/io/github/opencubicchunks/cubicchunks/core/util/WatchersSortingList3D.java#L131) always reports nonempty; [CuboidalCubeSelector:53](../src/main/java/io/github/opencubicchunks/cubicchunks/core/visibility/CuboidalCubeSelector.java#L53) tests the full visible volume for movement deltas. Existing `XYZMap` already uses dense arrays and unboxed coordinate access. | Snapshot player positions once per owner tick; give emptiness checks real state; compare entering/leaving slabs for small moves with the existing coordinate sets. Add gradual movement and multiplayer fixtures: the current disjoint teleport routes alone do not evaluate small-step delta algorithms. Preserve sparse/unbounded coordinate support. |
| Limit retained lighting-pool capacity | [PooledLightUpdateQueue:32](../src/main/java/io/github/opencubicchunks/cubicchunks/core/lighting/phosphor/PooledLightUpdateQueue.java#L32) can cache 4,096 segments with 4,096 ints each: **64 MiB of array payload per pool**, plus overhead, after a sufficiently large burst. This is a ceiling, not current measured occupancy or an up-front allocation. | Compare smaller/adaptive cache retention after a lighting burst and idle interval. Measure retained heap after the workload and later GC, not allocation sample weights. Test repeated bursts and queue reuse; modern GC cannot collect strongly referenced cached arrays. |
| Reduce client cache/rebuild allocations | `RenderCubeCache` allocates nested three-dimensional arrays and an empty `ExtendedBlockStorage` for every construction; rebuilt geometry repeatedly consults block/light data. | Profile allocation stacks during rebuild windows; compare flat arrays and lazy empty-storage creation. Preserve render-thread access, lighting behavior and missing-neighbor behavior. Inspect real captures and frame tails, not just a server trace. |

## What Java 9 through 25 adds here

The [local VM flag receipt](measurements/java25-opportunity-audit/java25-flags.txt) shows Temurin 25.0.3 supports compact headers, with them **disabled** by default; G1 is the selected ordinary-process default, ZGC is off, `UseAVX=2`, and `MaxVectorSize=32`. These are local default observations, not a new native benchmark or a claim about every JDK distribution.

| JVM capability | Fit to this fork | Boundary and initial test |
| --- | --- | --- |
| **Java 9: VarHandle and byte-array views** | Experiment with direct exact-size heightmap encoding instead of `ByteArrayOutputStream` + `DataOutputStream` + final array copy. A Java 8 baseline can use an exact byte array/`ByteBuffer`; compare against a Cleanroom-specific byte-array view handle. [VarHandle API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/invoke/VarHandle.html), [MethodHandles API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/invoke/MethodHandles.html) | Preserve endian order and every existing fixture byte. Start with normal scalar writes; handles do not automatically improve tiny writes. Do not weaken volatile/locking modes without a publication proof. Source compatibility needs an isolated modern implementation. |
| **Java 21: virtual threads, available in Java 25** | A candidate for many waiting storage requests after lifecycle/backpressure is defined. The current cube worker can wait on its column future; separate pools already prevent that dependency from starving columns. [Thread API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Thread.html), [adoption guide](https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html) | Keep world mutation and completion callbacks on the owner thread. Bound requests/native buffers/file contention independently of cheap threads. Compression/generation remains CPU work; test cancellation, shutdown and latency against a bounded platform-thread baseline. |
| **Java 22: MemorySegment/Arena** | A future experiment for explicit native-buffer or mapped-region lifetimes. The current RegionLib driver consumes `ByteBuffer`, and its readers call `.array()`, assuming heap-backed data. Integration needs buffer/stream adaptation and lifetime ownership. [MemorySegment API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html), [FileChannel API](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/nio/channels/FileChannel.html) | Preserve data-force → header-update → header-force ordering, overflow handling, cold reload and failure recovery. First fix the existing `ByteBuf` release path. Lower priority than the measured save work. |
| **Java 25: compact object headers** | A useful runtime-only A/B candidate for numerous `CubePos`, NBT tag/map and watcher objects. The installed VM accepts `-XX:+UseCompactObjectHeaders`; this can reduce header overhead. [GC considerations](https://docs.oracle.com/en/java/javase/25/gctuning/other-considerations.html) | Record the switch for one side at a time in fresh lab manifests/process receipts. Compare retained heap, allocations, GC and tick/frame tails with identical inputs. Header savings depend on layout/alignment and do not remove large array payloads. Full dependency/loader compatibility still needs a native run. |
| **Java 25: G1/ZGC runtime comparison** | Compare collectors if sustained allocation or measured pause windows warrant it. [Java command options](https://docs.oracle.com/en/java/javase/25/docs/specs/man/java.html) | Fixed heaps and workloads, separate server/client comparisons, GC events and CPU/wall-time evidence. The 314 ms observed autosave window reports zero GC collections, so reducing serializer work takes precedence for that stall. No collector change is made here. |
| **Java 25: incubating Vector API** | A later option for contiguous state-ID/nibble packing once a scalar palette/snapshot path exists. The module expresses SIMD computations. [Vector module](https://docs.oracle.com/en/java/javase/25/docs/api/jdk.incubator.vector/module-summary.html) | Requires module/launch handling and an isolated scalar fallback. Registry lookups, sparse height segments and branch-heavy neighbor lighting are poor starting kernels. Compare exact outputs and stable warmed measurements; do not infer a gain from API availability. |

Records, collection factories and scoped context APIs can improve implementation structure, but are not currently evidenced hot-path fixes. Keep modern-only implementations out of the Forge/Java 8 artifact. This review does not propose broad off-thread world access, preview-dependent core code, a wire/storage format change or copying newer Minecraft's generator implementation.

For collector/header A/B work the lab needs explicit, recorded per-side JVM options and hashes of referenced server argument files; its current CLI does not expose such options. Add that support and update the lab guide/skill before presenting a runtime-switch experiment as reproducible.

## Reproduction and first experiment sequence

The [isolated observations](measurements/java25-opportunity-audit/observations.json) record source state, probe source hash, actual compiled class hashes, named Minecraft JARs, libraries and commands. The diagnostic compiles one Java 8-compatible driver and runs it against both existing named artifacts. An identity-only scheduled-entry subclass avoids block-registration bootstrap; the collection failures are independent of its equality behavior. The NBT observation exercises the real array tag, while the lighting-writer relationship is established by source inspection. These runs use the available Cleanroom **0.6.13-alpha development API**, not the native 0.7.0 loader.

```powershell
# From E:\WorldGenOverhaul, after building both main artifacts as described in the lab guide.
.local/venv/Scripts/python.exe -B dev/CubicChunks-cleanroom/tools/probe_java_opportunities.py --output .local/cubic-lab/java25-opportunity-audit-next
```

Output names must be new. The tool observes current behavior; it is not a test suite that treats a known defect as desired behavior. When a finding is fixed, add its meaningful regression coverage and update its status rather than preserving an expected failure.

Recommended order:

1. Fix lighting snapshot ownership and scheduled-tick collection contracts with focused tests on both loaders; add native mutation and scheduled-block coverage.
2. Resolve the nullable batch-reader contract and reused-heightmap state before allocation-reuse experiments. Add compression/save failure fixtures before increasing asynchronous work.
3. Measure the two bounded structural changes separately: X/Z notification deduplication and exact packet sizing. Keep the current Riven generator/bounds and compare repeated fresh revisions with native streaming/captures and storage reloads.
4. Profile and budget owner-thread save serialization, then compare bounded compression scheduling. Use maximum ticks, not p95 alone, for autosave bursts.
5. Add recorded JVM-option support and try compact headers; use actual GC evidence to decide whether a collector comparison follows. Consider virtual-thread storage or vector kernels only after the simpler ownership/work reductions have measurements.

This preliminary pass adds diagnostics and a review record. It does not establish a performance improvement, full-pack compatibility or native reproduction of the listed failure paths.
